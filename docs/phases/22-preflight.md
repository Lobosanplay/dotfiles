# Pre-Phase 22 — Final State Audit

## Current architecture

Audit baseline: commit `a62f94a feat(dms): unify DankBar and muted desktop theme` on
`main`. The repository was clean at inspection (`main...origin/main`).

The static theme is authored in `themes/presets/default.json` as the semantic
Graphite Slate contract. `scripts/build-theme.py` validates it and generates
both `hypr/.config/hypr/modules/theme_tokens.lua` and
`dms/themes/graphite-slate/theme.json`. DMS selects the latter through its
custom-theme setting. Matugen remains controlled by DMS and generates its own
wallpaper-derived outputs. A project Matugen user template exports a separate
semantic dynamic-color overlay.

The live configuration is not fully the repository configuration:

- `~/.config/hypr/hyprland.lua` and the repository copy differ.
- Active `~/.config/hypr/modules/appearance.lua` has literal Graphite Slate
  border colors and shadow values. It does not require
  `modules.theme_tokens`; the active `modules/theme_tokens.lua` file is absent.
- Active `modules/dms.lua` matches the repository copy. It loads
  `dms.colors` after `modules.appearance`, so DMS-generated colors override
  the active appearance border colors.
- `~/.config/matugen` is a symlink to the versioned repository configuration.
- DMS's active `customThemeFile` points to
  `~/.config/DankMaterialShell/themes/dotfiles-graphite-slate/theme.json`.
  The older `dotfiles-graphite-blue` theme file remains on disk but is not the
  selected custom theme.

## Static theme flow

```text
themes/presets/default.json (Graphite Slate contract)
        ├── scripts/build-theme.py
        │      ├── hypr/.../modules/theme_tokens.lua (versioned output)
        │      └── dms/themes/graphite-slate/theme.json
        │                 ↓ copied/selected by the profile applier
        │         DMS customThemeFile (active Graphite Slate)
        └── component mappings/configuration
```

The static source of truth for versioned color roles is
`themes/presets/default.json`; schemas and templates validate/map it. Graphite
Slate is consumed by the DMS custom theme and by the repository-managed
Hyprland token module. The latter is not currently consumed by the active
Hyprland `appearance.lua`, which has equivalent muted literal colors instead.
Kitty's `dotfiles-theme.conf` currently provides opacity only, not the shared
palette. GTK's versioned settings set dark preference and icon theme; GTK's
active `dank-colors.css` is generated by DMS/Matugen, not Graphite Slate.

Graphite Blue is no longer the current preset or tracked DMS theme. It remains
in Git history and as an unselected user theme at
`~/.config/DankMaterialShell/themes/dotfiles-graphite-blue/theme.json`.
It is retained, not removed, as a historical/rollback artifact.

## Dynamic theme flow

DMS owns wallpaper selection and invokes its Matugen generation workflow. The
repository registers a Matugen user template in
`matugen/.config/matugen/config.toml` (active through the `~/.config/matugen`
symlink). Matugen renders the template to
`~/.cache/DankMaterialShell/dynamic-colors.pending.json`. Its post-hook runs
`scripts/promote_dynamic_theme.py`, which validates the candidate against the
semantic schema/contrast contract and atomically promotes it to
`~/.local/state/hyprland/dynamic-colors.json`.

DMS/Matugen also generates native component outputs, including
`~/.config/hypr/dms/colors.lua`, GTK `dank-colors.css`, and Kitty
`dank-theme.conf`. DMS's active Hyprland integration requires `dms.colors`
after the appearance module. DMS/Matugen's own outputs therefore already
supply live wallpaper-derived component colors (Hyprland borders in
particular), independently of the project's semantic JSON overlay.

The active DMS settings inspected select `customThemeFile` Graphite Slate and
`matugenScheme=scheme-neutral`. Their native widgets match the versioned
DankBar profile: launcher, tray, battery on the left; clock centered; CPU,
memory, temperature, and control center on the right. The active settings
also contain user-edited transparency values. No DMS settings were changed.

## Missing connection

`dynamic-colors.json` is not read by Lua, DMS/QML, GTK, or Kitty. It was last
modified at `2026-10-04 22:02` while the inspected DMS-generated Hyprland,
GTK, and Kitty outputs were modified at `22:19`; this confirms the semantic
export can be stale relative to the native outputs. Its existence alone does
not apply a theme.

The active Hyprland color path is currently:

```text
DMS Matugen → ~/.config/hypr/dms/colors.lua
                         ↓ loaded by modules.dms on Hyprland config load
                  live border colors
```

A new wallpaper palette updates generated files, but the repository contains
no project hook that consumes `dynamic-colors.json` and applies those tokens
to Hyprland or the selected DMS custom theme. The active configuration's
literal appearance values and its absence of the generated token module also
mean the versioned static mapping is not deployed there.

## Proposed integration point

Phase 22 should extend the existing DMS/Matugen user-template post-hook path,
not start another Matugen process or add a watcher/polling loop. After the
candidate has passed validation and is atomically promoted, a narrowly scoped
adapter can translate the validated semantic roles into an owned runtime
consumer, then request application through an established DMS/Hyprland
mechanism. The design must explicitly reconcile DMS's existing `dms.colors`
load order and the active-versus-versioned Hyprland configuration before
choosing whether the overlay augments or replaces generated border colors.

For DankBar, first confirm the supported DMS custom-theme refresh path for the
selected Graphite Slate file. Any dynamic output must remain generated and
user-owned, preserve the static Graphite Slate fallback, and avoid modifying
DMS files under `/usr/share` or overwriting DMS-generated files. Keep the
adapter idempotent, validate before writing, and avoid a full Hyprland reload
unless required and tested.

An existing piece that can be reused is DMS's generation event plus the
registered user-template `post_hook` and the atomic promotion script. DMS also
has a generic internal Hyprland `reloadConfig()` helper for its own
configuration operations, but inspection did not establish that theme
regeneration calls it. The project hook itself currently only promotes the
semantic JSON and does not signal/reload Hyprland or refresh DankBar. Do not
assume the internal helper is exposed as a supported extension API.

## Risks

- **Two competing dynamic sources:** DMS's native `dms.colors.lua` and the
  semantic overlay can describe different palettes. Applying both without an
  explicit precedence rule can produce inconsistent borders and bar colors.
- **Configuration divergence:** the active Hyprland appearance is not the
  versioned module and lacks `theme_tokens.lua`; editing only the repository
  may not affect the running desktop.
- **Reload failures:** blindly running `hyprctl reload` after wallpaper changes
  can expose unrelated active config errors or cause repeated reloads. The
  active config must be validated, and application should be conditional and
  failure-safe.
- **DMS settings ownership:** DMS may rewrite settings while running. Updating
  a custom theme file or settings directly can race with DMS; use supported
  refresh/application behavior rather than editing settings as a runtime
  mechanism.
- **Candidate/fallback integrity:** malformed or partially written output
  must never replace last-known-good colors. Retain the existing schema,
  contrast validation, same-directory atomic replace, and static fallback.
- **Timing and duplicate events:** palette generation can be queued; an
  adapter must not apply an earlier candidate after a newer wallpaper change
  or create an event loop.
- **Component scope:** DMS custom themes are global to DMS, not DankBar-only.
  A dynamic DMS theme change can affect other shell surfaces as well.
- **Verification access:** during this audit, user-bus access was denied, so
  DMS service/IPC state and live refresh behavior could not be confirmed.

## Phase 22 scope

Phase 22 should connect the already generated and validated dynamic palette to
the intended runtime consumers, using the existing DMS/Matugen event path and
without adding another palette generator. It should decide and document
precedence/fallback behavior, keep updates atomic, and validate the behavior
for a wallpaper change and an invalid candidate. The scope should be limited
to the theme adapter/hook, the minimum required active/versioned Hyprland
integration, DMS custom-theme refresh if supported, tests, and phase
documentation.

## Out of scope

No changes are needed for this integration to:

- WorkspaceGraph or WorkspaceOverview;
- Hyprland keybinds;
- monitor configuration;
- NVIDIA/PRIME;
- wallpaper rendering/selection itself;
- DankBar architecture or widget layout;
- DMS overlays under `/usr/share`;
- Matugen invocation or a second wallpaper service.

Do not implement a new watcher, polling loop, theme framework, or DMS shell.
